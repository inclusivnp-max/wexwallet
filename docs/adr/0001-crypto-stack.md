# ADR 0001. Криптографический стек: почему не Trust Wallet Core

- Статус: принято
- Дата: 2026-09-05
- Область: `security/*`, `chain/*`

## Контекст

Кошелёк поддерживает четыре несовместимые экосистемы: EVM, Bitcoin, Solana и
TON. Нужны деривация ключей, генерация адресов, сборка и подпись транзакций
для каждой из них.

Очевидный кандидат — [Trust Wallet Core](https://github.com/trustwallet/wallet-core):
одна библиотека на 130+ сетей, проверенная в продакшене на миллионах устройств.

Дополнительное требование: проект полностью открыт и рассчитан на внешние
контрибьюции и аудит безопасности.

## Решение

Отказаться от Trust Wallet Core. Использовать набор библиотек с Maven Central,
по одной на экосистему, плюс собственный модуль для EVM.

## Обоснование

Против Trust Wallet Core сыграли три довода, каждый из которых прямо
конфликтует с требованием открытости.

**1. Сборка требует персонального токена.** Android-артефакты раздаются только
через GitHub Packages, а этот реестр требует аутентификации даже для публичных
пакетов. Практически это означает, что `git clone && ./gradlew assembleDebug`
у стороннего контрибьютора не сработает: ему придётся завести personal access
token со `read:packages` и положить его в `local.properties`. То же касается
CI на pull request из форков. Барьер на входе там, где его быть не должно.

**2. Открытый блокер публикации в Google Play.** Нативная библиотека
`libTrustWalletCore.so` не проходит проверку выравнивания на 16 KB page size,
обязательную для приложений с targetSdk 35 и выше
([issue #4643](https://github.com/trustwallet/wallet-core/issues/4643),
[PR #4816](https://github.com/trustwallet/wallet-core/pull/4816) на момент
принятия решения не влит). Проект нацелен на targetSdk 37.

**3. Аудируемость.** Внешнему рецензенту проще прочитать Kotlin, чем
проверять, что подключённый C++ бинарник собран из тех исходников,
на которые ссылается документация.

## Выбранные библиотеки

| Слой | Артефакт | Обоснование |
|---|---|---|
| secp256k1 | `fr.acinq.secp256k1:secp256k1-kmp-jni-android` | Обёртка над libsecp256k1 от Bitcoin Core. Нативная, но проблема 16 KB у ACINQ решена — на этой библиотеке работает кошелёк Phoenix, опубликованный в Google Play |
| Bitcoin | `fr.acinq.bitcoin:bitcoin-kmp` | Сборка и подпись транзакций, BIP39/BIP32; активно поддерживается |
| EVM | собственный модуль `chain:evm` | RLP, EIP-155/1559/712 — небольшой объём кода, полностью покрываемый официальными векторами. Подпись переиспользует уже подключённый secp256k1, Keccak берётся из BouncyCastle |
| Solana | `org.sol4k:sol4k` | Kotlin, versioned transactions, Maven Central |
| TON | `org.ton:ton-kotlin-*` | Чистый Kotlin/KMP |
| KDF | `com.lambdapioneer.argon2kt:argon2kt` | Argon2id для ключа из PIN |

Официальный `org.ton:walletkit-android` рассматривался и отклонён: он требует
Android System WebView, то есть вносит JS-рантайм в путь подписи транзакции.
Для кошелька это неприемлемо независимо от удобства API.

## Последствия

Положительные:

- чистый клон собирается без единой учётной записи;
- нет блокера публикации в Google Play;
- меньше вес приложения: подключены только нужные сети;
- критичный код читается как обычный Kotlin.

Отрицательные и что с ними делаем:

- **Больше собственного кода в EVM.** Компенсируется официальными тестовыми
  векторами и перекрёстной сверкой подписей с `org.web3j:crypto`, который
  подключён **только** как `testImplementation` и в приложение не попадает.
- **Разная зрелость библиотек.** `ton-kotlin` — самая молодая из выбранных,
  поэтому TON идёт последним этапом с максимальным покрытием тестами и
  сверкой адресов с существующими кошельками.
- **Четыре зависимости вместо одной.** Обновления требуют внимания, версии
  зафиксированы в едином каталоге, изменения проходят ревью.

## Пересмотр

Решение стоит пересмотреть, если Trust Wallet начнёт публиковать артефакты на
Maven Central без аутентификации и закроет вопрос с 16 KB. Тогда wallet-core
может заменить часть реализаций за интерфейсами из `chain:api` без изменений
в UI и слое данных — ради этого интерфейсы и вводятся.
