# Участие в разработке

Спасибо за интерес к проекту. Ниже — всё, что нужно знать, чтобы изменение
прошло ревью с первого раза.

## Сборка

```bash
git clone <адрес репозитория>
cd WexWallet
./gradlew assembleDebug
```

Нужен только Android SDK 37. JDK 21 Gradle скачает сам. **API-ключи для сборки
не нужны и не должны быть нужны** — если ваше изменение ломает это правило,
оно не будет принято.

Перед отправкой pull request:

```bash
./gradlew build
```

Эта команда прогоняет сборку, unit-тесты, detekt и Android Lint — то же самое,
что делает CI.

## Установите git-хуки

```bash
./scripts/setup-hooks.sh
```

Ставит pre-commit, который проверяет коммит на утечку секретов. Это не
формальность: один случайно закоммиченный ключ — и его придётся отзывать,
потому что история git публична навсегда.

## Структура и границы модулей

```
feature → data → chain → core
```

- `feature/*` не обращается к `chain/*` и `data/*` в обход слоёв;
- `security/*` доступен только `data:accounts` и `feature:security`;
- `core/*` не зависит ни от чего внутри проекта, кроме других `core/*`.

Нарушение границ проверяется тестом на графе зависимостей в CI, поэтому такое
изменение просто не пройдёт.

## Стиль

- Форматирование задаётся `.editorconfig`, проверяется detekt (правила ktlint
  подключены через `detekt-formatting`). Длина строки — 120.
- Комментарии и документация — на русском, как и весь текст в репозитории.
  Идентификаторы и технические термины остаются в оригинальном виде.
- Комментарий должен объяснять **почему**, а не пересказывать код. Если
  комментарий дублирует строку ниже, он не нужен.
- Версии зависимостей задаются только в `gradle/libs.versions.toml`.

## Тесты

Обязательны для любого изменения в логике. Отдельно строго:

- код, который считает адреса, хеши или подписи, покрывается **официальными
  тестовыми векторами** соответствующего стандарта (BIP39, BIP32, SLIP-0010,
  BIP143, EIP-155, EIP-1559, EIP-712). Изменение без векторов не принимается;
- денежная арифметика покрывается граничными случаями: ноль, максимум,
  недостаток на комиссию, округление в свою и чужую пользу;
- сетевой слой тестируется на записанных ответах, а не на живой сети.

## Безопасность

Прочитайте [SECURITY.md](SECURITY.md) — раздел «Правила, обязательные для
кода» короткий и его нарушение блокирует ревью.

Новая зависимость в `security/*` или `chain/*` обсуждается в issue **до**
открытия pull request. Для остальных модулей достаточно обоснования в
описании изменения.

Если вы нашли уязвимость — не открывайте issue и не присылайте pull request
с исправлением. Порядок раскрытия описан в [SECURITY.md](SECURITY.md).

## Pull request

- Одно изменение — одна цель. Рефакторинг отдельно от новой функциональности.
- В описании: что меняется, зачем, как проверено.
- Изменения в поведении приложения сопровождаются обновлением README или
  документации, если она перестала быть верной.
- Коммиты на русском или английском, в повелительном наклонении:
  «добавить проверку адреса», а не «добавил» или «добавление».

## Дизайн-решения

Значимые архитектурные решения записываются как ADR в `docs/adr/`. Если ваше
изменение отменяет или заменяет решение, добавьте новый ADR со ссылкой на
предыдущий, а не переписывайте старый.
